# 架构说明

本文记录 QLink2Desktop 的分层结构、关键设计决策，以及与飞牛官方 fpk 规范的对齐方式。

## 1. 总体分层

```
        ┌──────────────────────────────────────────────┐
        │  webui（原生 ES 模块，go:embed，零构建）        │
        └───────────────────┬──────────────────────────┘
                            │ REST + SSE
        ┌───────────────────▼──────────────────────────┐
        │  httpapi   路由 / 鉴权 / 限流 / 事件广播        │
        └───────────────────┬──────────────────────────┘
                            │
        ┌───────────────────▼──────────────────────────┐
        │  app       装配 + 编排器（唯一知道全部零件处）   │
        └──┬─────────┬─────────┬─────────┬─────────────┘
           │         │         │         │
      ┌────▼───┐ ┌───▼───┐ ┌───▼───┐ ┌───▼──────┐
      │ store  │ │ fnos  │ │ proxy │ │discovery │
      │持久化  │ │桌面注册│ │反向代理│ │服务发现  │
      └────────┘ └───────┘ └───────┘ └──────────┘
           ▲
           │  domain（领域模型，被所有层依赖）
```

依赖方向严格单向：`domain` 不依赖任何人；上层通过窄接口协作，因此每个子系统都能独立单测。`httpapi` 里定义的 `Coordinator` 接口就是为了避免 httpapi 反向依赖 app 包。

### 与早期版本最大的差别

原实现把「用户想放什么到桌面」（定义）和「现在装了没有、代理活不活」（运行态）塞进同一个结构体，每次刷新状态都要重写一遍 JSON，还会把过期状态持久化下来。现在严格拆成：

- `domain.Link` —— **定义**，唯一被持久化的东西；
- `domain.Status` —— **运行态**，由 `fnos.Service` 与 `proxy.Manager` 实时回报，永不落盘。

## 2. 关键设计决策

### 2.1 端口是运行态，不该被持久化

反向代理监听在哪个端口，重启后可能变化。把它写进 `Link` 就等于持久化了一份过期事实。做法是给 `fnos.Service` 注入一个 `PortResolver` 回调，安装时实时询问；同时用 `stablePortStart`（FNV-1a 哈希 + 稳定排序）保证**两次独立启动分配出的端口完全一致**——否则每次重启端口都会漂移，所有桌面图标都得重装一遍。这一性质由 `TestPortAllocationIsStableAcrossRuns` 锁定。

### 2.2 期望与实际必须同源

「配置是否过期」的判定（`isStale`）和「实际写入磁盘的配置」（`writeUIConfig`）如果各写一份逻辑，两者一旦出现细微差异（比如一边补了 `allUsers=true` 另一边忘了），就会退化成**每次启动都判定过期 → 卸载重装 → 再判定过期**的死循环。

现在两者共用同一个构造函数 `BuildUIEntry`，并用 `TestBuildUIEntryMatchesWrittenConfig` 锁定「期望值 == 实际写入值」。

### 2.3 对账要克制

`Reconcile` 的判定结果是一个互斥枚举 `plan`（不动 / 唤醒 / 升级 / 安装），而不是一堆布尔量——布尔量之间能组合出无意义状态，枚举天然互斥，新增动作时编译器会提醒所有分支。

其中最关键的一条：**已就绪的项一律不碰**。早期版本每次启动都无差别重装，导致开机后桌面图标长时间抖动。现在由 `TestReconcileLeavesHealthyItemsUntouched` 断言「健康项不产生任何写操作」。

### 2.4 清理有安全闸，而且只认自己的命名空间

批量清理桌面图标是高危操作。`domain.IsManagedApp` **只**认本项目自己的前缀：

- `qlink2d.`（唯一被识别、唯一会被清理的命名空间）

早期的实现把另外两个前缀也列为"历史遗留前缀"，**这是错的，而且真的造成过事故**：那是其它独立工具的命名空间，用户完全可能同时装着它们并使用其生成的图标，把它们当孤儿清理属于越权删除（真实发生过一次误删用户图标）。

本应用与其它工具**没有任何数据血缘**：不识别它们的命名空间、不接管它们的图标、更不清理。

`appcenter-cli uninstall` 的真实实现里还有第二道闸，命中命名空间之外的包名直接拒绝。由 `TestCleanupOrphansOnlyTouchesOwnNamespace` 断言绝不触碰 `othertool.from-old-project`、`trim.photos`、`watchcow.dashboard` 这类第三方应用。

### 2.5 协议回退

经内置代理的桌面入口**必须**是明文 `http`：内置代理不做 TLS 终止，如果桌面图标写 `https`，浏览器会拿 TLS 去握手一个明文端口，直接失败。这条只对 `KindProxy` 成立（`fnos.Service.buildSpec` 里覆盖代理端口时同步把 scheme 摆正）；「本机端口」形态目前一律直连、不套代理，用户填什么协议就是什么协议。

### 2.6 飞牛 Connect 的可见性

外网子域名网关按 Cookie 域隔离鉴权。桌面入口若声明「仅管理员可见」，外网访问会被网关直接拒绝并报「FN Connect 暂无权限访问该服务」。因此凡是走端口的入口一律 `allUsers = true`——这是原项目踩过的坑，保留处理并在代码注释中记录原因。

### 2.7 SSE 与超时

SSE 是长连接，`http.Server` 上的任何全局写超时都会掐断它，表现为浏览器控制台的 `ERR_INCOMPLETE_CHUNKED_ENCODING`。因此只设置 `ReadHeaderTimeout` 与 `IdleTimeout`，不设 `WriteTimeout`。

### 2.8 启动闸门

安装完成后立刻点开图标时，服务可能还在初始化，此时网关会转发到一个还没监听的套接字上，用户看到 502。做法是 `cmd/main` 里放一个 `atomic.Bool` 闸门，就绪之前所有请求都返回一张自刷新的「正在启动」页（API 请求则返回带 `Retry-After` 的 JSON）。

### 2.9 统一网关下的路径基准（尾斜杠）

这是本项目在真机上排查时间最长的一类问题，单独记下来。

**现象**：页面永久停在「正在加载界面…」，控制台里既没有报错也没有失败的接口。

**机理**：`app/ui/config` 里声明的入口 URL 是 `/app/qlink2desktop/`，但飞牛统一网关会把末尾斜杠吃掉，iframe 实际拿到的文档 URL 是 `/app/qlink2desktop`。HTML 里所有资源都是相对路径（这是为了不绑定前缀，见下），此时浏览器把基准目录算成 `/app/`，于是：

```
assets/app.js   →   /app/assets/app.js     ← 不匹配网关前缀，404
```

JS 根本没加载，所以控制台干净得可疑。

**为什么不能只在后端解决**：网关是否把 `/app/<name>` 前缀转发给后端，各飞牛版本不一致。

| 网关行为 | 后端看到的路径 | 后端能否自行 302 补斜杠 |
| --- | --- | --- |
| 剥掉前缀 | `/` | **不能** —— 后端不知道对外前缀是什么 |
| 保留前缀 | `/app/qlink2desktop` | 能，已实现（`buildDispatcher`） |

只要存在「剥掉前缀」的版本，后端方案就一定有覆盖不到的场景。**只有浏览器自己知道它请求的是哪个 URL**，所以规范化必须放在前端。

**做法**：在 `index.html` 的 `<head>` 里、**所有 `<link>` / `<script src>` 之前**放一段同步内联脚本，**同步注入 `<base>`**：

```js
if (p !== '/' && !p.endsWith('/') && 末段不含 '.') {
  var base = document.createElement('base');
  base.href = p + '/';
  document.head.appendChild(base);
}
```

三个约束缺一不可：

1. **必须在所有相对资源之前**——放在 `<body>` 末尾就已经晚了，请求早已发出；
2. **必须同步执行**——不能写成 `type="module"`，模块脚本是延迟执行的；
3. **判据是「末段不含点」**——本 SPA 全部使用 hash 路由（`#desktop` / `#discovery`），路径段恒定，因此这条判断既能命中应用根目录，又不会误伤 `/assets/app.js` 这类真实文件请求。

### 为什么是注入 `<base>`，而不是 `location.replace(...)`

第一版写的是 `location.replace(p + '/')`，看起来更"正统"，但有个实测出来的副作用：**`replace` 是异步的**。本函数返回后 HTML 解析器会继续往下走，把后面那批相对资源按**旧基准**发出去 —— 于是控制台先炸出一片 404，等重定向回来才恢复正常。

```
404 /app/assets/app.js      ← 重定向生效前的抢跑请求
404 /app/icons/default-64.png
（重定向后一切正常）
```

那串红字极具误导性：看起来就像应用坏了，实际只是抢跑。`<base>` 在本行立即生效，后面的资源第一次就解析到正确地址 —— 省掉一次整页加载，控制台也干净。保留 `location.replace` 仅作为取不到 `document.head` 时的兜底。

> 残余噪声：Chromium 的**预扫描器**（preload scanner）会抢在解析器之前按文档基准预取 `<link>` / `<script src>`，这一条无法从 HTML 侧消除，因此无斜杠入口下仍会看到 1～2 条 404。应用本身不受影响（解析器用的是 `<base>` 之后的正确地址）。这也是下面「启动期自诊断」要把版本号常显出来的原因之一。

后端那段 302 保留着不删：它零成本，且能覆盖「保留前缀」的网关版本，两者互为兜底。

> 在 `<head>` 里做路径规范化并不是唯一做法：另一条常见路线是用 `location.replace` 跳到带斜杠的地址。本项目改用同步的 `<base>`，理由见上一条（跳转是异步的，后面那批相对资源仍会按旧基准发出去）。

### 2.10 启动期自诊断（看门狗）

起因是一次真实事故：**新包装上了，浏览器却仍在跑上一版的 `app.js`**。旧版按旧的目录布局 import，于是 9 个子模块全部 404，界面停在启动页，而服务端一切正常 —— 现场只有一张控制台截图，靠的是人工放大截图才读出那 9 条 URL。这条路必须堵死。

两个方向同时下手：

**（一）让"跑错版本"这件事不可能发生**

| 手段 | 作用 |
|---|---|
| `?v=<版本号>` 资源 URL | 文件名不带哈希，换 URL 就等于绕开旧缓存 |
| `Cache-Control: no-store` | 入口 HTML 与全部静态资源都不留副本，任何中间层也无法钉住旧版本 |

**（二）万一带到了错误资源，页面必须自己把证据摆出来**

难点在于：**诊断代码不能写在 `app.js` 里**。`app.js` 本身就是被加载的目标之一，它加载失败时，写在它里面的错误界面永远不会执行 —— 用户能看到的只有一只永远转的圈。

所以诊断放在 `index.html` 的同步内联脚本里，做三件事：

1. **采集资源失败**：资源错误不冒泡，必须在捕获阶段监听（`addEventListener('error', fn, true)`）；
2. **看门狗**：12 秒仍未进入应用，就把版本号、文档 URL、失败清单写进 `#boot-detail` 并亮出重试按钮；
3. **自己走一遍 import 图**：模块图里任何一个子模块 404，浏览器只会在控制台丢一句**没有文件名**的报错，而这正是最需要的信息。看门狗因此会 `fetch` 入口模块、正则解析其中的静态 `import` / `export ... from`，递归两层，把取不到的 URL 连同 HTTP 状态逐个列到页面上。

故障版（把 import 改回旧布局）的实测输出：

```
版本 v1.2.7-degraded · 超过 12 秒仍未就绪
文档：/app/qlink2desktop
入口模块 assets/app.js 没能执行：它自己或它 import 的子模块没有取到。
最常见成因是浏览器复用了旧版本的缓存文件。
处理：按 Ctrl+Shift+R 强制刷新；仍不行就卸载后重装本版。

取不到的文件：
  HTTP 404  .../assets/dom.js
  HTTP 404  .../assets/api.js
  ...（共 9 项）
```

另外，启动卡片上**常显版本号**（`v<版本>`）。这样任何一张故障截图都能自证"装的是哪一版"，省掉反复确认包名的来回。

**这段内联脚本是全项目最不能出错的一段代码**：它一挂，路径守卫与看门狗同时失效，页面就退回"只转圈、什么都不说"。而常规的 `.js` 语法检查覆盖不到内联脚本，所以 `scripts/check-js-imports.py` 专门把它抽出来交给 `node --check` 单独校验。

### 2.11 `hidden` 属性与作者样式的层叠陷阱

这是本项目出过最隐蔽的一次事故，值得单列一节。

**现象**：新版装好后，界面永远停在「正在读取配置与桌面应用…」，转圈不停，**控制台干净得没有一条本项目相关的错误**。看起来像是启动逻辑卡住了，但服务端正常、`app.js` 也执行了（启动文案就是它写的）。

**真相**：应用**早就正常启动了**，只是启动遮罩永远盖在上面。

`[hidden] { display: none }` 来自浏览器**默认**样式表。在层叠规则里，作者样式表的任何一条普通声明都优先于默认样式表 —— 于是本文件里这三行把它彻底架空：

```css
.boot { display: flex; }   /* → boot.hidden = true 变成空操作，遮罩永不消失 */
.app  { display: grid; }   /* → app.hidden  = true 同理 */
.btn  { display: inline-flex; }  /* → 本该隐藏的「重试」按钮一直露着 */
```

于是 `showShell()` 里那句 `boot.hidden = true` 什么也没做。用户看到的是"打不开"，代码里却找不到任何失败。

**修法**：加一条兜底规则，比逐个元素去改 `display` 可靠得多。

```css
[hidden] { display: none !important; }
```

**为什么原来没被发现**：验证脚本读的是 `el.hidden` **属性**，而属性一直是 `true` —— 断言永远通过。要发现它必须看**计算样式**，而且光看元素自身的 `display` 还不够：父链上有 `display:none` 时，子元素的计算值仍是它自己的 `block`。正确判据是 `Element.checkVisibility()`（会连带祖先链一起判断）。

现在两层都守着它：

| 层 | 检查 |
|---|---|
| 服务端（`e2e-gateway-check.py`） | 送出的 CSS 里必须有 `[hidden]{display:none}`（匹配前先剥掉注释，否则解释这条规则的注释会顶替掉规则本身而"通过"） |
| 运行时（`browser-boot-check.js`） | 动态把 `hidden` 加到 `.boot` 上读计算样式，另断言 `#boot` 真的不可见、`#boot-retry` 处于初始隐藏态 |

两处都做过反向验证：删掉那条 CSS 规则，静态与运行时检查分别报出 2 项与 3 项失败。

> 教训可以推广成一句：**任何"属性已设置"的断言，都不能替代"用户真的看不到"的断言。** 涉及显示与隐藏的检查，一律以计算样式为准。

### 2.12 异步响应模型：慢动作不许进请求路径

起因是真机上一张「请求超时：15 秒内没有响应（api/links/item-…）」的截图。

**真相**：那条报错是**假的**。删除时后端先落盘、再调 `appcenter-cli` 注销桌面图标，而单条 CLI 命令的超时上限是 3 分钟（删除含 stop + uninstall，最坏 6 分钟）。前端的网络预算是 15 秒，于是先超时了 —— 但服务端还在正常干活，链接大概率已经删掉了。

把时间线摆出来就很清楚：

```
0s      用户点删除
0.01s   落盘完成（这一步其实早就成功）
0.01s   开始跑 appcenter-cli stop  ← 分钟级
15s     前端超时，弹出「请求超时」
…       服务端继续跑
~40s    卸载完成，一切正常
```

**根因不在超时设得短，而在响应模型**：把分钟级的外部命令放进了秒级的请求路径。加大超时只是把假报错推迟，治不了本。

**做法**：请求路径只负责**受理**。凡是要碰 `appcenter-cli` 的动作（注册 / 注销 / 对账 / 清理）一律交给 `Coordinator` 的串行后台队列，接口立刻返回当前阶段。

| 动作 | 请求路径同步做完的部分 | 交给后台的部分 |
| --- | --- | --- |
| 新建 / 保存 | 落盘 | 建代理 + 注册桌面图标 |
| 删除 | 落盘 + 回收代理监听 | 注销桌面图标 |
| 启用 / 停用 | 落盘 | 注册 / 注销桌面图标 |
| 重新同步 | 校验存在性 | 全量同步 |
| 对账 / 清理遗留 | 受理 | 全部 |

四条硬性约束：

1. **context 必须跟随进程，不能继承 `r.Context()`**。请求一返回它的 context 立刻被取消，继承它等于让任务刚动手就被掐断 —— 这是异步化最容易写错的一行。
2. **串行执行**。`appcenter-cli` 内部要抢应用中心的锁，并发调用只会互相拖慢，还让"谁先谁后"不可预测。串行之后每件都以最快速度跑完，排在后面的在界面上显示「排队中」。
3. **入队即反映状态**（`PhasePending`），并且**必须走到终态**。曾经 `PhaseInstalled` 是从未被赋值的死常量，异步化后如果不同步落终态，那一行会永远停在「排队中」—— 一个不会自愈的假进度。
4. **状态变化必须广播**。装配层把 `Server.BroadcastStatus` 注入到 `Coordinator.SetOnChange`；没有这一环，前端永远收不到「排队中 → 已就绪」，异步改造等于白做。

**接口层的契约随之收紧**：`httpapi.Coordinator` 接口**只暴露 `Queue*` 受理型方法**，压根没有同步版本。想在那个接口上加同步调用，先回答一句「这个动作的耗时上限是多少」。

**前端也有一半责任**，两件事缺一不可：

- 写操作要有**独立的**超时预算（`MUTATION_TIMEOUT_MS`），不能和只读请求共用 15 秒；
- 超时后**必须回查真实状态**，不能把「可能已成功」报成硬失败。删除超时就重新拉列表看这条还在不在 —— 不在就是删掉了。否则用户会再点一次，然后撞上"链接不存在"的二次报错。

**可观测性**：`/api/system` 暴露 `pending_jobs`，「系统与日志」页显示队列深度，桌面页的副标题显示「处理中 N」。有了它们，「排队中」是自愈中的进度还是卡死，一眼可分。

这套性质由 `internal/app/coordinator_queue_test.go` 锁定（受理不阻塞、串行执行、通知回调、队列满明确失败、退出可取消），并由 `e2e-gateway-check.py` 在接口层断言 202 受理语义；两处都做过反向验证。

### 2.13 网址快捷方式只能借 CGI 302 跳出去

**现象**（用户真机截图）：建一个指向 `https://www.baidu.com` 的「网址快捷方式」，点开却是「飞牛登录地址 + 百度网址」拼成的一串怪 URL。

**真因——桌面入口的地址是拼接出来的，主机名那一截永远是飞牛自己**：

```
{protocol}://{当前浏览器 hostname}:{port}{url}
```

`ui/config` 里**没有任何字段**能指定主机名：内网访问时它是 NAS 的 IP，走 FN Connect 时它是飞牛的中继域名。于是把 `url` 写成 `https://www.baidu.com`，拼出来的就是 `http://<NAS>:<端口>https://www.baidu.com` —— 正是截图里那个地址。

这个规则有两处独立佐证：

1. 飞牛官方社区《关于 fpk 应用入口跳转任意地址的分享》：文中明说"port 为空则跳转飞牛端口……我们发现链接的大多数地方都可以填写，但是 **ip 不行**"，并给出的可行办法就是**借助 CGI 输出 302 跳转**；
2. 第三方 fnOS fpk 开发 Skill 里对同一规则的等价表述。

**走过的弯路**：中间一版新增了第四种路由 `routeExternal`，把入口 `url` 直接写成绝对外链，并且**写进了这一节的文档、写进了四条测试用例**。它在本机 E2E 里"验证通过"了 —— 但那些断言只能证明"包里的 config 写的是什么"，永远证明不了"飞牛怎么解释它"。把前者当成后者来汇报，是这次事故里方法论上的错误。

**现在的形态**（`fnos.decideRoute` 只剩两种）：

| 形态 | 入口 URL | 是否生成 `index.cgi` |
| --- | --- | --- |
| 有端口（本机 / 映射） | 相对路径走端口入口 | 否 |
| 无端口（快捷方式等） | `/cgi/ThirdParty/<app>/index.cgi` | 是 |

判定只有一条：**有真实端口就直连，没有就走 CGI 302**。

**CGI 脚本是双保险的**（`fnos.cgi.go`）：

1. 主进程可用 → 带上 `--mode cgi` exec 过去，由 Go 侧发 302；
2. 主进程不在（服务没起来、socket 路径不对）→ 脚本自己输出 `Status: 302` + `Location:`，避免直接掉进"白屏 / 错误页"；
3. 两条路都不通（极端情况下 CGI 输出被丢弃）→ 还有一张 HTML 兜底页，`meta refresh` + JS 双路重定向。

**三个注入面必须分别处理**，因为同一个目标地址会同时进三份上下文：

| 落点 | 处理 | 不处理的后果 |
| --- | --- | --- |
| HTML 兜底页 | `html.EscapeString` | 目标里带 `<script>` 就被执行 |
| shell 变量 `FALLBACK_TARGET` | `shellQuote`（单引号） | 空格 / 引号把脚本语法搞坏 |
| `Location:` 响应头 | `sanitizeTarget` 剔除控制字符 | 单引号在 sh 里**可以跨行**，回车会造成响应拆分 |

由 `TestBuildPackageShortcutUsesCGI302`、`TestBuildPackagePortlessWithoutTargetIsExplicit`、`TestBuildPackageEscapesRedirectTarget`、`TestSyncShortcutUsesCGI302` 锁定。最后一条是**第三次重写**的：它先断言"必须走 CGI"，后改成"必须走外链"，现在又改回 CGI —— 三次都对应一次真机结论，注释里留了完整记录。

**遗留风险**：「规矩上的限制」和「CGI 执行失败」是两回事。用户最早报的 `/cgi/ThirdParty/<app>/index.cgi/redirect/...` 错误页属于后者，尚未定位（怀疑顺序：可执行位 → socket 路径 / 主进程未运行 → 网关前缀转发差异），本机没有 NAS 真机证据。

### 2.14 局域网扫描：扫对网段，且必须异步

这一节由两张真机截图催生：**扫描结果里只有 172.17 网段、一台设备都没有**；以及**点扫描后弹「请求超时：15 秒内没有响应」**。

**（一）网段判定：虚拟网卡陷阱**

早期 `LocalSubnets()` 遍历所有非回环网卡，于是把 `docker0`（172.17）、`br-xxxx`（172.18）当成本机网段 —— 扫的是容器网络，真实设备一台也扫不到。判定顺序因此改为：

> 默认路由出口网卡 > 其它物理网卡 > 虚拟网卡（仅在找不到任何非虚拟候选时才用）

「上级网段」是默认网关**不在**本机 /24 时网关所在的那个 /24；网关与本机同段时它为空 —— 这是拓扑事实，不是失败，界面上要如实说明"本段已包含网关，请改用自定义范围"。

范围解析（`ExpandRangeSpec`）支持整段 / 单台 / 区间 / CIDR / 主机名 / 粘贴的网址，上限 1024 台；**超限直接报错而不是截断**——悄悄只扫一部分比明确拒绝更糟，用户会以为"扫过了，没有"。

**（二）异步：扫描不许进请求路径**

一个 /24 × 46 个常见端口 = 上万个 TCP 连接，真机十几秒起步，必然撞上前端 15 秒预算。形态与 §2.12 同源：

```
POST   /api/discovery/scan    202 + 任务快照（受理即返回，带 id / range / hosts_total）
GET    /api/discovery/scan    进度与结果（前端每 800ms 轮询一次）
DELETE /api/discovery/scan    取消（幂等：没任务在跑也返回 200）
```

三条实现约束：

1. **同一时刻只允许一轮**。`ScanRunner.Start` 遇到已有扫描在跑，不报错也不排队，而是把正在跑的那轮原样交回 —— 用户连点两次"开始扫描"想要的是看到进度，不是一个"已在扫描"的报错。
2. **两阶段**：先对每台主机探 16 个探活端口筛出在线设备，再只对在线设备跑完整端口表；范围 ≤ 32 台时跳过探活（用户明确列了几台机器，要的就是"这些都扫一遍"）。代价要在界面上说清：某台设备在线但一个常见端口都没开时可能被跳过，把它的 IP 填进自定义范围再扫即可。
3. **热路径要廉价**：进度计数用 `atomic`，结果与阶段文案用互斥锁，两者刻意分开；探测用固定数量 worker 轮转取任务，而不是"每个目标一个 goroutine"（后者数量随目标数线性增长）。`context` 跟随进程，不继承 `r.Context()`。

前端对应的一半责任同样不可省：**扫描状态放在全局 `state.scan` 里，而不是视图的闭包里**。这个视图每次刷新都是整体重绘，状态留在闭包里等于"扫到一半切个页签，结果全没了"。

由 `internal/discovery/scanjob_test.go`（范围解析、路由表解析、虚拟网卡降级、上级网段推导、Runner 受理 / 取消 / 拒绝超限）与 `e2e-gateway-check.py`（三端点 + 非法范围 400 + 首选网段不是虚拟网段）共同锁定，两处都做过反向验证。

### 2.15 统一的「使用帮助」界面

四种能力（本机端口 / 端口映射 / 网址快捷方式 / 远程主机）在列表里长得几乎一样，但"点开图标之后会发生什么"完全不同 —— 尤其远程主机：列表长得和别处一样，不解释的话没人知道登记一台机器之后会发生什么。把说明散进各个卡片的 `hint` 里解决不了这个问题，因此集中成独立一页，每张卡片只讲清一件事：它解决什么问题、怎么用、有什么坑。

两条入口，缺一不可：

- **侧边栏常驻一格**（放在最后）。它不参与日常操作，但需要时必须在同一个列表里找得到，而不是藏在某个角落的链接里；
- **顶栏一个按钮，对每个视图都在**（帮助页自身除外）。说明写在帮助页里还不够：用户是在"正要操作却不知道这一步会怎样"的那一刻需要它，那一刻他多半在某个具体页面上。远程主机页另外在表头下方放了一段就地说明 + 「查看完整说明」跳转。

一个容易忽略的细节：**帮助页的 `refresh()` 刻意不重绘**。这是一份长文档，而应用每收到一次状态推送都会通知当前视图刷新 —— 跟着重绘会把用户读到一半的滚动位置拽回顶部。页面内容不依赖运行态，重绘没有任何收益。

内容与代码同源、一起发版：文档写在仓库里没人看，写在界面里才会被看到。由 e2e 的静态守卫盯着"导航里注册了 help 视图"与"帮助页模块经网关可取得到"，避免它退化成一份谁也打不开的文档。

### 2.16 界面主题：明暗 × 色系，且必须在首帧之前生效

两个**正交**的选择：明暗模式（`light` / `dark` / `auto`）× 色系（六套）。落地方式是往 `<html>` 上写两个属性，由样式表用 `[data-theme=…]` / `[data-accent=…]` 选取变量，布局代码与颜色完全解耦。

```
<html data-theme="dark" data-accent="violet">
```

`data-theme` 上写的**永远是解析后的 `light` / `dark`**，不是 `auto` —— CSS 只需要认两种底，"跟随系统"这一步用 `matchMedia` 在进入页面前就地算掉。

色系只声明三个量（`--a-h` 色相 / `--a-s` 饱和度 / `--a-l` 实心按钮明度），派生色由模式段统一算出：文字色、实心按钮、柔和底、聚焦环。**新增一套色系只要加一行**，不必复制整套变量 —— 这也是为什么色卡预览用的示例色和真实取色能保持相近而不重复维护。

三个坑，都在这一层，都不会报错，只会让界面"看起来不对"：

1. **主题必须在首帧之前生效。** 后端配置要发一次请求才拿得到，注定赶不上第一次绘制；深色用户每次打开都会先闪一下白底（FOUC）。因此偏好存 **localStorage**，并且 `index.html` 里有一段**同步内联脚本**（位于 `<link rel=stylesheet>` 之前）抢先写属性。theme.js 的 `STORAGE_KEY` 与内联脚本里的字面量必须一致，**e2e 有静态守卫盯着**——不一致的后果正是"首帧按默认值画、进了应用才跳过去"。
2. **加色系时容易漏掉一处。** `theme.js` 的 `ACCENTS`、`style.css` 里对应的 `data-accent` 段、`index.html` 内联脚本里的白名单，三处都要有。漏了 CSS 段是**静默回落成蓝色**（选了没反应），漏了内联白名单是**首帧用蓝色、随后才变**。前两处已有静态守卫。
3. **`.field > .segmented` 要 `align-self: flex-start`。** `.field` 是纵向 flex，默认 `align-items: stretch` 会把 `inline-flex` 的分段控件拉满整行 —— 按钮仍挤在左边，背景却铺了一整条，看起来像坏了。

主题是**本机偏好**，不写服务端配置。两个理由：它必须在首帧之前生效（只能读 localStorage），以及同一台 NAS 上不同设备想用不同底色是合理需求，不该互相覆盖。

### 2.17 重启本应用服务：异步，且**不能把故意的断开报成故障**

停止命令会终止执行它的那个进程。因此 `/api/system/restart` 是受理型（202），请求路径**根本等不到**"重启完成"那一刻 —— 等到的只会是自己的连接断开。

#### 后端：为什么不能在本进程里「Stop 再 Start」

飞牛只提供 `appcenter-cli start / stop`，**没有 restart**（`--help` 确认过）。第一版就照着"stop → sleep → start"写在本进程里，真机上**必然把应用停死**，而且原因不是代码写错，是这条路在机理上走不通：

```
22:53:13 POST /api/system/restart → 202
22:53:14 [main] Stopping qlink2desktop...
22:53:24 [main] send KILL signal to PID:516508...
22:53:25 [main] qlink2desktop stopped.        ← 应用此后再也没起来
```

`appcenter-cli stop` 是**同步**的：它调用应用自己的 `cmd/main stop`，后者向本进程发 TERM，再每秒轮询等它退出（10 秒宽限，超时 KILL）。也就是说 **Stop 返回之前本进程已经不存在了**，"之后再 Start" 那几行永远执行不到。它还会顺带把优雅退出卡死：`Service.Stop` 阻塞在等 `appcenter-cli`，而 `appcenter-cli` 在等我们退出，于是 `Coordinator.Stop()` 里的 `wg.Wait()` 永远等不到。

现在的做法是把「等 4 秒 → stop → 等 3 秒 → start」整条链交给一个**另立会话（setsid）、不属于本进程**的 `/bin/sh`（`internal/fnos/detach_unix.go`），本进程只负责把它点着就返回。`cmd/main` 的 `stop_process` 只 kill PID 文件里那一个 PID，不波及另立会话的子进程。脚本里的每一步都 `echo` 到 `<LogDir>/restart.log` —— **那段脚本比写它的进程活得久**，它失败时（start 报错、应用中心忙）那几行是唯一的线索，没有它就只剩一个"停掉之后再也没起来"的应用。

两段等待都不是可调的感觉值：4 秒是**交接**（让 202 先回到浏览器、前端来得及弹等待层，太短用户会以为点崩了），3 秒是**静置**（等应用中心把套接字收干净，太快 start 会读到上一个进程残留的 socket，表现为"重启完点开还是 502"）。另外 `stop` 包在 `if/else` 里，**失败也继续 start** —— 最坏的结果不是"没重启成功"，而是"停掉之后再也起不来"。

顺带修掉的一处顺序问题：退出时必须**先 `CloseEvents()` 再 `srv.Shutdown()`**。`Shutdown` 会等所有连接变空闲，而 SSE 是长连接永不变空闲 —— 排在前面就永远等不到，每次停止都耗满宽限再被应用中心 SIGKILL。

真正的难点在前端，而且是体验事故的高发点：**把一次故意的断开报成"失败"，用户会以为没重启成功然后再点一次。** 所以前端分三件事：

1. 派发 `qlink:restarting` 事件，外壳据此**先关掉 SSE**。否则 EventSource 会立刻报错重连，侧边栏飘一个假的「实时已断开」，而实际上一切正常。
2. 调接口后**只在被服务端明确拒绝（4xx）时报错**。超时 / 连不上 / 网关 5xx 全都说明进程已经开始重启了 —— 继续往下走。
3. 弹一个**不可关闭**的等待层，每 2 秒轮询 `GET /api/health`（公开端点，不带鉴权，因此会话恢复前也能探活），服务一回来就整页重载。进程是全新的，链接状态、日志缓冲、SSE 连接全部失效，整页重载比增量修复省事得多，也不会留下一个半新半旧的界面。总预算 120 秒，超时才亮出「手动刷新」。

应用中心命令行不可用时（模拟模式）按钮直接置灰并把原因写进 `title`：重启靠的就是 `appcenter-cli` 的 stop/start，与其让用户点了之后收到一句报错，不如在按下去之前就说清楚。

守护它的东西有三层：

1. `internal/httpapi/server_test.go`：`TestRestartEndpointIsAccepted`（响应必须是 202 且任务入队一次）与 `TestRestartEndpointWithoutCoordinator`（只读模式下**不能**假装受理 —— 返回 202 会让前端进入等待轮询，而服务其实什么都没做）。
2. `internal/fnos/restart_test.go`：**真的 spawn 一次**脚本（`restartShell` 在开发机上指向 Git Bash 的 sh），看 `calls.log` 里是不是落下了 `stop\nstart\n`；并单独验证 **stop 失败时 start 照样执行**。只断言脚本文本是不够的 —— spawn 失败、路径被引号吃掉、顺序反了都不会体现在文本里。反向验证时这条报的是 `最后读到 "stop\n"`，与真机症状一字不差。
3. e2e 的静态守卫：接口与前端是否接上、是否进入等待轮询、是否与外壳协作关掉了 SSE、`RestartSelf` **函数体内**不许出现 `s.cli.Stop(`（整文件搜会命中 Uninstall / PruneOrphans 那些合法调用，守卫会形同虚设，所以按函数体截取）、`detachSysProcAttr` 必须 setsid、`CloseEvents()` 必须排在 `srv.Shutdown` 之前。事件名匹配的是**带引号的完整事件名** `'qlink:restarting'`：只搜裸子串的话，拼错成 `qlink:restarting-x` 也会命中，等于没在测（这一条是在反向验证时发现的）。

> 附带一条本机踩坑：Go 是原生 Windows 程序，它 spawn 的 Git Bash `sh` 会对自己的 argv 做「Win32 ↔ POSIX」路径转换，脚本里任何 `/c/...` 形式的绝对路径都会被改写成 `\c\...`，于是脚本**静默失败**。所以那两条执行类测试用的是包目录下的相对路径（`restartTestDir`）。

### 2.18 端口转发：与反向代理是互补的两层，不是重复

`internal/forward` 是四层（TCP / UDP）转发，`internal/proxy` 是七层（HTTP）反向代理。
两者都要在本机起监听，看上去很像，**但它们能做的事几乎不重叠**，因此没有合并：

|                    | proxy（七层）      | forward（四层）        |
| ------------------ | --------------- | ------------------ |
| 认识的内容              | HTTP 请求与响应      | 字节流 / 数据报，不理解内容    |
| 能承载的服务             | 只有 HTTP         | SSH、RDP、SMB、数据库、DNS、游戏…… |
| 独有能力               | 按域名路由、跳过自签证书、改写响应 | 协议可选 TCP / UDP / 两者 |
| 端口                 | 自动分配的 18000 段   | 用户自己指定              |

选错的代价很高：用端口转发去代理网站"能用"但拿不到证书豁免；用端口映射去转发 SSH 则根本连不上。
所以帮助页把这张表直接摆在界面上，而不是只写在文档里。

#### 规则模型

`domain.Forward` 只承载定义，运行态（`forward.Status`：是否在监听、累计字节、最近失败原因）
由 Manager 实时合成、不写盘 —— 与 `Link` / `Status` 的分离是同一条原则。
规则持久化在**独立的 `forwards.json`**，不混进 `links.json`：一处文件损坏不该连带丢掉另一类数据。

#### 三种必须拦住的错误配置，以及"什么时候拦"

这是本模块最花心思的地方。三种错误配置的**性质完全不同**，因此拦截时机也不同：

| 错误配置                  | 性质                | 时机                             |
| --------------------- | ----------------- | ------------------------------ |
| 自转发（8080 → 127.0.0.1:8080） | 配置本身的错误，不改就永远不会好 | `Validate()`，返回 400            |
| 两跳环（A→B 且 B→A）          | 同上                | `Manager.Check()`，**落盘之前**，返回 409/400 |
| 端口被本应用的另一条规则占用         | 同上                | `Manager.Check()`，**落盘之前**，返回 409 |
| 端口被本应用**之外**的程序占用       | 环境的暂时状态，随时可能变好   | 照常落盘，`Apply` 失败时作为 **warning** 返回 |

第四行是刻意的取舍：那个程序随时可能被关掉，如果因为它占用端口就拒绝保存，
用户连配置都存不下来，只能先去别处解决问题再回来重填一遍表单 —— 毫无必要。
但前三行如果也照常保存，就会留下一条"存下来了但永远起不来"的规则，
用户每次打开都要重新判断一次。所以 `Check()`（只判断不监听）与 `Apply()`（真的启动）
必须分开：前者挡确定性错误，后者允许失败。

自转发检测里还有一处细节：`0.0.0.0` 与 `::` **不是**回环地址，但在 Linux 上对它们拨号
同样会被解释成本机，因此必须由 `IsUnspecified()` 一起覆盖。判据刻意只写在**一处** ——
早先 `switch` 里列了这两个字面量、下面又判了一次 `IsUnspecified()`，结果反向验证时
删掉其中任意一处测试都不会失败：两处都能达成同一个结果时，测试就守不住任何一处。

同理，环检测只查**两跳**。真实的转发配置几乎不会超过两跳，而两跳环恰恰是手工配置
最容易配出来的（想把两个端口都暴露出去，手一滑就把目标端口对调了）。真机上它一旦发生，
一个数据包会在两个端口之间无限弹射，几秒内吃满 CPU。

#### 绑定形态：写死双栈会变成"别的工具能跑，这里不行"

这是本模块出过的一个真实故障：用户报「同样的设置，别的工具就能跑，这个程序报端口已被占用」。
两条规则的端口、协议、目标完全一致，差别只在**绑定形态**。

Go 里 `net.Listen("tcp", ":18080")` 是**双栈**监听（Linux 上落在 `[::]` 且 `v6only=0`），
它要求 **IPv4 与 IPv6 两侧都空闲**——只要有一个程序占了其中一侧（比如某个服务只绑了
`0.0.0.0:18080`，或某个进程以 `v6only=1` 占了 IPv6 侧），整个监听就失败。
而只绑单栈的工具此时完全不受影响，于是用户看到的就是"它行、这个不行"。

修法不是"换个端口"（端口该由用户决定，见下），而是**留空监听地址时给绑定形态留退路**
（`internal/forward/listen.go`）：

1. 先 `:port`（双栈）：覆盖最广，绝大多数情况下的正确答案；
2. 再 `0.0.0.0:port`（仅 IPv4）：救"IPv6 侧被占"；
3. 最后 `[::]:port` + v6only（仅 IPv6）：救"IPv4 侧被占"——IPv4 回不来了，
   但至少让 IPv6 访客能用，而不是整条规则趴着。

只有 `isAddrInUse` 才继续试下一种形态；端口非法、权限不足这类与形态无关的错误
立即返回——换个协议栈再试一次不会有不同结果。
**用户显式填了监听地址时只有一个候选**（`bindFixed`）：替他改地址比如实报错更糟，
他会以为自己配的地址生效了。

退化必须**说出来**：`[::]:18080` 在"双栈"与"仅 IPv6"两种情况下字符串完全一样，
但后者意味着 IPv4 的访客连不上。所以状态里带 `bind_mode`，界面上标出
「监听中 TCP · 仅 IPv4」，并在日志里告警。否则用户会以为"转发坏了"，
而真相是占用者占了另一侧、我们退到了这一侧。

#### 占用者诊断：只说"被占用"等于没给线索

端口冲突的提示必须回答"**是谁**占着"，否则用户只能瞎猜。
Linux 上直读 `/proc/net/{tcp,tcp6,udp,udp6}` 找出处于 LISTEN（TCP 状态 `0A`、
UDP 未连接 `07`）且本地端口匹配的 socket inode，再扫 `/proc/<pid>/fd` 里的
`socket:[inode]` 软链反查进程与 comm。

刻意**不依赖 `ss` / `lsof`**：这两者在精简系统上未必装得全，而 `/proc` 一定在。
非 Linux 平台返回空（宁可不猜，也不造一个没人验证过的近似版本）。

三个容易写错的点：

- **内核把端口写成四位补零的大写十六进制**（53 → `0035`）。按 `%X` 拼成 `35`
  永远匹配不上，而且 8080 恰好是四位、肉眼看不出来——这个 bug 是单测抓出来的。
- 只比**本地**端口，不能拿远端端口一起比。
- 占用者若是**本进程自己**，提示必须说"本应用自己"并指向 18000 段的桌面应用链接，
  而不是报一个 PID。对用户报自己进程的 PID 等于没给线索
  （最常见的成因就是内置反向代理先占了这个端口）。

另外，「端口被占用」这句话与错误类型会叠成
`端口已被占用: 端口 18080 已被…占用`，读起来很糟。所以 `ErrPortInUse` 的文案改成
`监听端口冲突`，把具体端口交给上下文去说。

#### 端口区间不是我们能管的

内置反向代理会在 18000–18999 里为桌面应用链接自动分配端口，与端口转发共用同一个
端口空间却互不知情。**不要因此去限制用户能填哪个端口**——端口选择权在用户，
我们能做的是把冲突查清楚、说清楚（「检查端口」按钮 + 上面的占用者诊断），
而不是替他缩小范围。

#### UDP：会话表与回收

UDP 没有连接，也就没有 FIN——转发层必须自己维护「源地址 → 到目标的 socket」这张表，
并自己决定何时回收。这是整个模块唯一需要显式生命周期管理的地方，
也是 UDP 转发最常见的泄漏点：功能一切正常，fd 与内存在几周里慢慢涨上去。
回收由 `reapLoop` 按 `udpIdleTimeout`（60 秒）扫描，会话被回收时必须同步归还并发信号量，
否则并发上限会"只减不增"，跑一段时间后所有新连接都被拒。

回包必须用**监听的那个 socket** 写回，不能另开一个：对端与途中的 NAT 是靠
"响应来自我发往的那个端口"来认领回包的，换一个源端口发出去会被当成来历不明的包丢弃。

#### TCP：半关闭

两个方向各一个 goroutine 做 `io.Copy`，但**不能**简单地等两边都结束再 `Close`。
很多协议靠"我发完了"这个信号结束一次交互（HTTP/1.0 短连接、不少自定义 TCP 协议），
所以每个方向拷完后要调 `CloseWrite()` 半关闭，让对端读到 EOF 而不是被硬生生掐断。
漏掉这一步的表现是"请求发出去了但响应永远不回来"。

字节数通过 channel 回传而不是写共享变量：两个方向确实是并行的，
`<-copied` 天然完成了同步，不需要额外的锁。

#### 访问控制

每条规则可设白名单 / 黑名单，列表项支持单个 IP 与 CIDR。
解析不出来源 IP 时：白名单模式拒绝（fail-closed，放行等于给安全策略开口子），
黑名单模式放行（fail-open，"只挡这些"不该株连认不出来的人）。

`normalizeIP` 会把 IPv4-mapped IPv6 地址（`::ffff:192.168.1.5`）归一化成 IPv4 形式：
双栈监听下同一个对端可能一会儿报 IPv6 写法、一会儿报 IPv4 写法，
不归一化的话一条写 `192.168.1.5` 的白名单会在 IPv6 路径上神秘失效 ——
这类"有时能用有时不行"的问题最难查。

#### 可观测性

每条规则累计连接数、活跃数、双向字节数、被拒 / 失败 / 超限次数，
并保留最近 100 条连接记录（环形缓冲，不是无界切片 ——
一条配置错误的规则每秒可能产生成百上千条记录）。
连接记录单独一个接口（`GET /api/forwards/{id}/connections`），
不合并进列表接口：列表每次刷新都要打，而记录只在用户点开某条规则时才需要。

守护它的东西有三层：

1. `internal/forward/forward_test.go`：**真的转发一轮数据**（起一个回显后端，
   连监听端口发数据、收回包、校验计数），UDP 会话回收、ACL 的十种情况、
   自转发 / 两跳环 / 端口冲突 / 停用释放端口。
   只断言"监听起来了"是不够的 —— 监听成功但双向拷贝写反、或半关闭漏了，
   一样起得来、一样连得上，只是数据永远回不来。
2. 反向验证覆盖四处：去掉 TCP 回程、关掉环检测、关掉 UDP 回收、
   去掉 `IsUnspecified`，每一处都能让对应测试 FAIL。
3. e2e 的静态守卫（+14 条）：接口层不许自己 `net.Listen`（分层）、
   自转发 / 环检测 / UDP 回收 / 半关闭 / ACL 归一化必须存在、
   `Check()` 必须在落盘前、外部占用必须给 warning、
   路由注册齐全、持久化独立文件、前端三处接上（视图 / 导航 / 事件）、帮助页讲清区别。

> 一处测试自身的坑值得记：客户端读到回包的那一刻，转发层**还没**更新计数
> （它在等另一个方向的 goroutine 收尾）。直接断言计数等于赌调度顺序 ——
> 单次跑几乎必过，`-count=8` 或与其它包并行跑时随机失败。
> 那种"偶尔红一次"的测试比一直红更耗时间，因为它会让人怀疑被测代码。
> 现在统一走 `waitFor` 轮询等待。
>
> 另：`-race` 在本开发机上跑不了（Windows 无 gcc，`-race` 需要 cgo）。
> 带 gcc 的环境应补跑一次 `go test -race ./internal/forward/`。

### 2.19 窄屏导航：一条"元素存在"查不出来的可见性故障

用户报「手机模式下左侧的侧边栏没有了，不能切换功能区」。截图上那一行只剩一个孤零零
的「7」徽标和两个状态点 —— 七个功能项**都在**，只是看不见、也点不准。

根因是一条看起来毫无问题的窄屏规则：

```css
/* 本意：窄屏空间紧张，只留图标 */
.nav-item span:not(.nav-badge) { display: none; }
```

但导航项的图标**本身也是 `span`**：

```html
<button class="nav-item">
  <span class="nav-icon">图标</span>   <!-- 被这条规则一起藏掉了 -->
  <span>桌面应用</span>                <!-- 这个才是想藏的 -->
  <span class="nav-badge">7</span>
</button>
```

于是图标与文字一起消失，只剩徽标 —— 有徽标的那一项变成一个数字气泡，其余六项变成
**37×14px 的空白按钮**。手指点不准，视觉上"侧边栏不见了"。

**写选择器时，`元素类型 + :not(某 class)` 会把同类兄弟节点一并命中。**
要隐藏的是"文字"这种**语义**，就必须给它自己的 class（`nav-label`），
而不是按它恰好是什么标签来选。

修法同时把导航从"顶部图标条"改成**底部固定条**：飞牛的 App 在页面之上还有自己的
标题栏与系统状态栏，窄屏顶部已经被吃掉两行，而底部是拇指最容易够到的位置。
具体约束：
- 每项 `min-height: 46px`（触摸目标下限 44px）；
- 徽标改为绝对定位浮在图标右上角，否则有徽标的那一项会比邻居高；
- `.content` 必须自己给底部条留白 —— 底部条是 `position: fixed`、不占文档流，
  不留白的话最后一张卡片永远滚不到；
- 宽屏（>860px）仍是左侧栏，行为不变。

#### 条高与留白必须同源

`.sidebar` 的 `min-height` 和 `.content` 的 `padding-bottom` 用的是**同一个变量**
`--navbar-h`：

```css
:root { --navbar-h: 58px; }              /* ≤400px 的屏为 56px */
.sidebar { min-height: calc(var(--navbar-h) + env(safe-area-inset-bottom, 0px)); }
.content { padding: 14px 14px calc(var(--navbar-h) + 24px + env(safe-area-inset-bottom, 0px)); }
```

早先是两个互不相干的数字（46 与 78）。改了一处忘了另一处，表现是"最后一张卡片被压
在栏下面"或"底部空一大截"——**单看任意一边都是对的**，只有把它们放在一起比才看得出来。
所以静态守卫要求两处都出现 `var(--navbar-h)`，浏览器守卫要求
`padding-bottom ≥ 底部条实测高度`。

变量里**不含**安全区，安全区在各自的计算里再加一次：`env(safe-area-inset-bottom)`
在有虚拟导航键 / 全面屏手势条的手机上不为 0，不加的话条会被系统条压掉一截。
`viewport` 另带 `interactive-widget=resizes-content`，让安卓软键盘压缩内容而不是把
整个视口顶上去。

#### 为什么这条故障溜过了全部既有校验

图标 span **一直在 DOM 里**，`hidden` 属性从未被设置过。
任何"元素存在吗""属性是什么"的断言都看不见它。更阴的是，用 Playwright 的 `.click()`
能强制点中任何元素 —— **包括看不见、点不准的**，所以"点一下能切换"也会假通过。
因此 `scripts/browser-mobile-check.js` 一律：
1. 用 `checkVisibility({checkOpacity, checkVisibilityCSS})` 判"看得见"；
2. 量 `getBoundingClientRect()` 的实际尺寸；
3. 用 `page.mouse.click(x, y)` 按**真实坐标**点，而不是 `.click()`；
4. 先断言 `navCount >= 6` —— 否则元素一个都没渲染出来时，所有"逐项都合格"
   会因为集合为空而空过（0 项里没有不合格的，断言就"通过"了）。

#### 侧边栏只放导航：徽标与状态点都已下线

侧边栏每项右侧曾经挂过一个计数徽标（条目数），中间还专门修过一次**懒加载**：
数字取自 `state.links / discovery.ports / forwards / icons`，而这四个列表原先各自只在
**自己视图的 `mount()`** 里填充 —— 没进过那个页面就没有数据，用户的原话是"每次都得
点击一下才能显示出来那个数值"。修法是 `bootstrap()` 里统一拉一次。

**然后用户要求把它整个去掉**（"把这个侧边栏的数字和圆圈显示效果都去掉"）。
去掉时连带删掉的就是上面那段统一拉取 —— 这两件事的成本是对称的：
为了让它"一进来就对"，要先知道会付出什么代价（四份列表 + 一个启动期请求）。

现在侧边栏**只有导航**：计数留在各页面自己身上（列表标题、筛选器），
导航只负责"去哪一页"。窄屏的状态点也一并撤掉 —— 那里 `.pip-text` 本来就是隐藏的，
两个点退化成一枚没有任何文字的绿圆点，"除了占空间没有其他的用处"。
宽屏保留（那里有"应用中心可用 / 实时已连接"这样的文字）。

对应的守卫是**断言节点数**而不是"被 CSS 藏起来了"：
```js
document.querySelectorAll('.nav .nav-badge, .nav .nav-item [class*="badge"]').length === 0
```
留一堆藏起来的节点，换个断点就会重新冒出来；而且"藏起来"意味着数据仍然要有人去拉。

**通则：界面上的计数类元素，要问"它的数字从哪来、什么时候来"，而不是只问"它渲染了没有"。**

### 2.20 「自动」图标：去目标站点抓 favicon

用户报的是「这个自动获取图标，能不能直接自动抓取，一般就是通过直接抓 url 的 favicon
来获得的」。「自动」这一档原先只有一条路 —— 拿容器镜像名去官方图标库匹配，
匹配不到就用内置默认图标。后果是**内网服务永远拿不到自己的图标**：
公开图标库里不会有人替你收录自家 NAS 上跑的那个服务。

现在的顺序（谁先成功用谁）：

```
上传 → 文字 → data URI / 裸 base64 → 远端 URL
     → 官方图标库匹配（人工挑选，质量最稳）
     → 站点自己的 favicon          ← 本节
     → 内置默认图标
```

#### favicon 排在官方图标库之后，是有代价计算的

图标库那一套是人工挑的，质量稳定；favicon 是"退而求其次但仍然对得上"的一档。
放在后面有两个好处：不必为**每个**链接都发一次站点请求（这段代码跑在
「保存 / 放到桌面」这条用户正在等的路径上），也不会拿一张 16×16 的 favicon
去顶掉一枚干净的官方图标。

#### 两条互补的线索

| 线索 | 覆盖的情况 |
| --- | --- |
| 页面里的 `rel="icon"` / `apple-touch-icon` / `msapplication-TileImage` | 现代站点普遍只声明 PNG，根目录根本没有 `.ico` |
| 站点根目录的 `/favicon.ico` | 纯前端应用（HTML 里什么都没有）与老站点 |

取的是**根**目录而不是当前路径下 —— 带路径的服务（`/admin`）也把图标放在站点根上。
`apple-touch-icon` 排在最前，因为它通常就是 180×180 的 PNG，缩放到 64/256 比
16×16 的 `.ico` 干净得多；`rel="mask-icon"` 是单色 SVG，标准库解不了，直接跳过。

#### ICO 必须自己解，否则整条路会「看起来没生效」

`/favicon.ico` 绝大多数就是 ICO 格式，而 **Go 标准库没有 ICO 解码器**
（`image.Decode` 直接报 unknown format）。不自己解的话，这条最主流的路径会
**全程失败**，表现是"改了代码但图标还是默认的" —— 最难查的那种形态。

`decodeICO` 做两件事：
- 从目录里挑**面积最大**的一档（同一枚 favicon 里常有 16/32/48/256 各一份；
  用 16×16 放大到 256 会糊成一团）；
- 内容可能是 PNG（现代做法，直接塞一张 PNG 进 ICO），也可能是 DIB 位图
  （1/4/8/24/32 位）。

DIB 那条有两个坑：**高度是整个图像的两倍**，多出来的一半是 1 位 AND 掩码
（1 = 透明；32 位图自带 alpha，通常忽略掩码）；行是**自下而上**存的。
另外有些老工具生成的 32 位 ICO 完全不填 alpha（整张全 0），照原样用会得到一枚
全透明的图标 —— 在桌面上就是"没有图标"。这种按不透明处理。

#### 抓取必须有总预算

一段代码最多试 4 个候选地址。如果每个候选各自设 5 秒超时，最坏会拖到二十几秒，
而用户正卡在"保存"那一刻等它。所以用 `context.WithTimeout` 卡**总**预算（5 秒），
无论试几个候选，到点就收工。失败结果也进缓存 —— 一个没有 favicon 的地址在
每次桌面图标对账时都会被重新解析，不记下"这里什么都没有"就等于每次都白等一次超时。

#### 地址从哪来

`iconSiteURL(l)` 按链路形态给出**真正提供页面的那个地址**：

| 形态 | 地址 | 为什么 |
| --- | --- | --- |
| 网址快捷方式 | 用户填的目标网址 | 就是它本身 |
| 反向代理 | 后端真实地址 | 代理端口此刻可能还没起来，而后端地址是用户填的、确定存在的 |
| 本机端口 | `http://localhost:<port>` | 服务就在本机，问回环地址最直接 |

拿不到地址（没填 host / port）就返回空串，这一档自动跳过 —— 不凭空造一个地址出来。
带自签证书的站点要用户在链接上勾选「忽略自签证书」，否则这一步取不到；
这正落在内网服务最常见的形态上，所以 `faviconClient(insecure)` 按开关分了两个客户端。

整档受 `--no-remote-icon` 管辖：**关掉远端图标时这一步必须一起跳过**。内网地址
看起来无害，但那仍然是本进程主动建立的连接，用户关掉的就是这个授权。

### 2.21 图标解析的过程必须对用户可见

#### 故障现象与真正的病根

用户报的原话是：

> 我弄了个百度的网站快捷方式，这个图标也没有自动搜索百度的图标啊，
> **这个过程有个什么提示吗或者能让人知道搜索中或者搜索状态**

随后补充：

> 不光是说弄快捷方式，其他的本机端口和端口映射也是有这样的问题，
> 当我选择了一个本机内部的程序、或外部链接、做端口转发或者是端口映射的时候，
> 这个图标功能并没有自动下载或找到他对应的图标，而且过程也没有提示

截图里编辑器「图标 → 自动」那一格永远画着内置默认图，旁边一个字都没有。

**按现象去查抓取本身，会得出错误结论。** 实测 `fetchSiteFavicon("https://www.baidu.com")`
是能拿到 1024×1024 的；真正的问题是**结果与过程都没有回传**：

1. `iconPreviewSrc()` / `thumbSrc()` 对"自动"档一律返回内置默认图 ——
   前端从来没向后端问过解析结果；
2. 解析只发生在打包那一刻，结果只写进桌面包，面板上没有任何回音；
3. 于是「还没去找」「去找了没找到」「根本没找（离线开关关了）」三种
   完全不同的情况，在界面上**完全同形**。

这也解释了为什么三种链路形态（本机端口 / 端口映射 / 网址快捷方式）都有同样的问题 ——
病根在展示层，与形态无关。

#### 做法

**解析结果带上"它是怎么来的"**：`ResolveIconEx` 返回 `IconResolution`，
除图标本身外还有 `Source`（七档之一）、`Detail`（一句给用户看的话）、
`Site`、`Elapsed`。`ResolveIcon` 保留为它的薄壳 —— **解析链只能有一个实现**。

> ⚠️ 这条不是洁癖。守卫原先盯着 `ResolveIcon` 的函数体，拆分之后它们就变成了在
> 检查一个没人调用的壳，而"守卫盯着错的函数"与"守卫全绿"长得一模一样。
> 所以现在有一条守卫专门钉死这层委派关系。

**新增 `POST /api/icons/resolve`**：接收一条**链接草案**（可以没名字、没填完、
没落库），同步解析后返回来源、说明、站点地址、耗时与一张可直接显示的 data URI 预览。
做成同步而非后台任务：这一档本来就有总预算（favicon 5 秒 + 官方图标库 6 秒），
前端配一个「正在查找…」的转圈恰好覆盖这段时间；做成异步只会多一套轮询，
用户等待的绝对时间一点没少。

**编辑器「自动」档**：一进这一档就查一次，期间显示转圈 +「正在查找图标…」，
结束后换成结论标签（成功绿 / 警告黄 / 失败红）+ 说明 + 耗时，旁边有「重新查找」。
改端口 / 换形态 / 改地址会自动重查（700ms 防抖 + 令牌双保险：防抖省请求，
令牌保证迟到的结果不会覆盖新结果）。

**列表缩略图**：`EnsureAutoIcon` 把解析出的 64 档落盘为 `icons/auto-<linkID>.png`，
`View.IconAuto` 随列表下发，`thumbSrc` 优先用它，悬停显示来历（`IconAutoNote`）。

为什么不改成"前端逐条调解析接口"：一个有二十条链接的页面会同时打出二十个
可能访问外网的请求。本项目在飞牛统一网关下已经踩过"并发转发表不可靠"这个坑
（见 §2.12），列表页绝不能再做成 N 个并发请求。落盘之后，列表拿到的只是一个
本地 PNG 的地址。

#### 两个必须踩到的坑

**① 解析接口必须宽松解码。** 它收到的是前端直接回传的**整条链接**表单数据，
而它自己只用得上几个字段。用严格解码的话，链接以后每加一个字段都会把这个预览打挂 ——
第一次真机/浏览器验证就撞上了 `json: unknown field "desc"`，
报错内容和图标八竿子打不着，界面上只表现为"查找失败"。
真正落库的写入接口仍然一律严格解码。

**② 官方图标库匹配也必须卡总预算。** 这一档是乘法：候选数 × 关键词数 × 4 个 CDN 节点。
国内访问 jsDelivr 经常整体不通，每一次都要等满单请求超时（8 秒）——
最坏能在这条"用户正等着看图标"的路径上挂好几分钟。现在卡 6 秒总预算，
到点就交给 favicon 那一档（对内网服务来说，那一档才是真正能命中的）。

#### 验证方式

「正在查找…」是一个**只在请求进行中存在的瞬时状态**：静态守卫能查到代码里有
那行字，查不到它有没有被画到屏幕上、有没有被样式压没、是不是一帧就闪过去了。
所以另有一个真视口脚本 `scripts/browser-icon-check.js`，它**故意把解析请求拖慢
1.2 秒**（靠时序碰运气的话，本机连接被拒是毫秒级返回的，那一态根本抓不到），
再断言：转圈可见、文案正确、状态行有实际高度、结束后收敛成明确结论、
失败用警告色而不是成功色、预览图是 `data:image/png;base64,`。
"有提示"的对立面是"节点建了却没 append"—— 那在静态文本里看不出来，
在浏览器里一眼就能看出来。

### 2.22 服务发现：内核按套接字记账，用户看的是服务

**现象。** 用户报：「为什么扫描出来的端口是重复的，有 0.0.0.0 的有不带的，
然后窗口最大化之后又再重复出来了很多」，并附了两张截图。

**病根有两层，都不在"扫描"上。**

**① 粒度错位：`/proc/net` 按套接字记账，界面按服务展示。**
一个服务往往占好几个套接字：

| 服务 | 套接字 | 原因 |
| --- | --- | --- |
| `sshd :22` | 2 | `net/tcp` 的 `0.0.0.0:22` 与 `net/tcp6` 的 `:::22` |
| `rpcbind :111` | 4 | 上面两份 × tcp/udp 各一份 |
| `nmbd :137` | 十几个 | 上面四份之外，还在**每一个网卡地址**上各绑一份 |

于是飞牛的统计卡写着"监听端口 101 个"，其中真正不同的服务不到二十个，
屏幕上就是一片看起来一样的卡片。

**② 协议被当成兜底来显示。** 原来的 `portItem` 第二行是
`[镜像, 地址, 用户].join(' · ')`，协议只在**第二行为空时**才顶上去：

```js
h('div', { class: 'line2', text: sub || p.proto.toUpperCase() })
```

同地址同端口的一对 tcp / udp 套接字因此渲染成**两条一模一样的行** ——
用户看到的"重复"里最刺眼的那部分就是这个。

**做法。**

- 新增 `internal/discovery/group.go`。`GroupPorts` 把同一服务的多个套接字
  收成一行：合并键是**进程 + 端口**。协议不进键（同一服务的 tcp 与 udp
  是同一件事），地址不进键（地址是要收集的信息，不是身份），容器也不进键
  （容器信息是被 `Enrich` 按端口贴上去的**信息**，算进身份只会让"某个套接字
  恰好没被贴上容器"变成一条幻影重复）。不同进程占同一个端口
  （SO_REUSEPORT、容器映射与宿主机服务各一份）靠键里的进程分开。
- `PortInfo` 增 `Addresses` / `Protos` / `Scope`。合并后仍把完整地址名单带出去 ——
  界面据此说出"这个服务对谁可见"。`Address` 降级为"代表地址"，
  仅供仍然只认单地址的调用方；**界面不用它**：nmbd 那种绑了十一个网卡地址的
  服务，挑哪一个当代表都是误导（按字典序第一个往往落在 docker 的网桥地址上）。
- 「所有网卡 / 仅本机 / 指定网卡」是一个**判断**，只在 `ClassifyScope` 里做一次。
  前端不许自己去比字符串 `"0.0.0.0"` —— 两处判据迟早不一致，
  而且 `::` 在界面上会被当成"没有地址"（用户说的"有不带的"就是它）。
- 协议移到**端口号下方**自己的位置，永远显示。放第二行末尾会被 `truncate`
  砍掉，而它正是用来区分"看起来一模一样的两个套接字"的那一点信息。
- 统计卡改称「监听服务」，并在提示里给出**合并前**的内核套接字数
  （`Scanner.Listening` 的第二个返回值）。收敛必须暴露：101 → 二十来个，
  不说清楚第一反应一定是"漏了一堆端口"。这两个返回值刻意**不拆成两个方法**：
  拆出来的那个只回列表的便捷方法没人调用，而一个没人调用的壳看起来和
  "有这条能力"一模一样（本项目踩过）。
- `GroupPorts` 是纯函数，和 `ParseProcNet` 同一个理由：这段逻辑最容易出错，
  但不能依赖真的跑在一台 Linux 上才能测。

**一个被自己的测试打脸的中间版本。** 初版写了一段"先到的套接字读不到进程名时，
让后到的补上"。测试直接证明了它**永远不执行**：进程名 / PID / 用户名来自同一次
`/proc/<pid>/fd` 查找，要么一起读到要么一起读不到，而 `groupKey` 又要求同一行的
进程相同。留着的死代码比没有更危险 —— 它让"这里做过容错"看起来是真的。
现在只对两类**由外部注入**的信息（容器、桌面标记）做"不留空缺"的合并，
并在注释里写明为什么不写逐字段补全。

**关于"窗口最大化之后又再重复出来了很多"。** 查过了：应用里没有任何
resize 处理，`replace()` 也是先 `clear` 再 `append`，改视口本身不会重绘，
行数不会增长。真实感受来自两点叠加：列表是 `repeat(auto-fill, minmax(258px, 1fr))`，
窗口变宽后每行塞下更多列，同一批重复项一下全铺在眼前；截图又是整屏的。
不过**"重绘必须替换而不是追加"这件事本身值得盯住** —— 它正是"又再冒出来很多"
这类现象的唯一可能成因，所以真视口脚本里加了一步"点一次「重新扫描」再数行数"
（重绘必然发生），并在反向验证里用「把 `clear(node)` 从 `replace` 里删掉」来证伪。

**验证方式。** `scripts/browser-discovery-check.js`（真视口，17 条）：
把 `/api/discovery/ports` 的响应**替换成夹具**（本机是 Windows，根本没有
`/proc/net`，等真实数据的话这一段会"零个元素里没有不合格的"式空过），
夹具里**故意放一对没有合并的 tcp/udp**，用来验证即便后端哪天不再合并，
光靠渲染也不会出现两条一模一样的行：

- 每一行都写出协议、且真的可见有高度；
- 把所有行的 `端口 + 协议 + 标题 + 副标题` 当成"身份"去重，重复数必须为 0；
- 那一对"故意没合并"的 smbd 445 必须仍然分辨得出来；
- 绑在多网卡地址上的服务被归纳成「N 个网卡地址」，悬停能拿回完整清单；
- 改视口（1680×1000 / 760×800）以及点「重新扫描」后，行数与去重后行数都不变。

夹具的形状（`addresses` / `protos` / `scope` 三个字段名与取值）由 Go 侧单测
`TestPortInfoJSONCarriesGroupedFields` 钉住 —— 字段改名或 `omitempty` 把值吃掉时，
前端只会显示空白，而所有单测照样全绿。两边合起来才是完整的一条链。

### 2.23 缩放：别把 logo「压缩太狠」

**现象。** 用户换了一版 logo 之后补了一句要求：

> logo 的图别压缩太狠，有用户反映图标都不清楚了。

**为什么一定会糊。** 这条链上做的**全是缩小**：飞牛桌面图标只有 64 / 256 两档，
而来源普遍是 512～2048 见方。1536 → 64 是 24 倍，一步双线性每个输出像素只采样
源图上 4 个点 —— 99.6% 的源像素根本没被读到，细线条断裂、文字糊成一团。

**两层病根，各修一处。**

1. **近似。** 旧实现是「反复 2×2 盒式折半，缩到目标两倍以内再双线性收尾」。
   折半本身没问题（等价于区域平均），但每一步都是一次近似，收尾那次双线性
   又只采样 4 个点。改成**精确面积平均**：每个源像素按它与输出像素覆盖区
   重叠的面积加权，一步到位，少一层近似就少一层模糊。

   受控实验（1536 源，拉普拉斯平均绝对值当锐度指标）显示这一步的收益很小 ——
   64 档 64.02 → 70.33，只有 4%。**真正丢清晰度的不是它。**

2. **缺锐化。** 面积平均本身是个低通滤波，边缘一定会被摊平，缩得越狠摊得越平。
   所以缩到 2× 以上时补一道 3×3 轻度锐化（中心 5、四邻 -1，`amount = 0.20`）：

   | | 面积平均 | 面积 + 锐化 0.20 | 面积 + 锐化 0.35 |
   | --- | --- | --- | --- |
   | 64 档锐度 | 64.02 | **97.71** | 113.67 |
   | 64 档边缘色噪 | 15.95 | **57.81** | 76.27 |

   0.35 的锐度只多一点点，边缘色噪却明显更脏 —— 所以取 0.20。
   仓库里那版旧产物的锐度是 64.86，也就是说这一步把清晰度提高了一半。

**锐化必须在预乘 alpha 空间做。** 非预乘的 RGB 在 alpha 边缘处是"不可靠"的：
一个全透明像素的 RGB 是什么颜色，对结果毫无意义。直接对它做拉普拉斯，会把
"只存在于 alpha 上的跳变"当成颜色跳变来放大 —— 图标外圈于是泛起品红 / 青色
噪点，64 档肉眼可见。预乘之后透明区的 RGB 被拉到 0，边缘的颜色才真正只由
"看得见的那些像素"决定。

**只锐化颜色，不锐化 alpha。** 轮廓的透明度是抗锯齿的成果，动它会在图标外圈
留下一圈忽明忽暗的硬边。

**缩得少就不锐化。** 2× 以内丢掉的细节有限，硬上锐化只是把噪声和锯齿一起
放大。所以 `ResizeHighQuality` 里按 `sw >= dstW*sharpenMinRatio` 判断；
尺寸完全相同时更是直接返回，连"预乘 → 插值 → 反预乘"那一趟都不走
（uint8 往返会带进 ±1 误差，而那里本该是恒等变换）。

**顺带修掉的同类问题。** 放大路径（用户上传一张 32 见方的小图时）原本在
**非预乘**空间插值，会让透明区的黑色渗进边缘，图标外圈套上一圈灰描边 ——
和上面是同一个 bug 的两副面孔，一起改成预乘空间。另外 `BoxDownscale`
（反复折半那个近似）在新管线里没有调用点了，直接删掉：留着它就是"缩放有两条
路径"，而两套实现并存时产物走哪一条取决于调用点，改了 A 看起来"没生效"。

**为什么这条链上的图都必须过同一个入口。** 产品图标的 5 个产物、运行时的
默认图标（`DefaultIcon`）、浏览器标签的 favicon、用户上传的图标、文字渲染的
图标 —— 全部经过 `ResizeHighQuality`。所以"改了缩放看起来没变化"的排查
一定能收敛到这一处；反过来说，任何绕开它的第二条路径都会造成"应用中心的
图标清楚了、桌面上的还是糊的"。

**验证方式。**

- `internal/fnos/imageutil_test.go`：面积平均必须逐像素等于按覆盖面积手算的
  期望值（4×4 → 2×2 整倍数验等权、3 → 2 非整数倍验**加权**）；纯色缩放后
  颜色不变；全透明像素的颜色一个字节都不许渗出来；放大后颜色不许变暗；
  锐化不得改动 alpha；512 → 64 的边缘能量必须比面积平均高出 10% 以上
  （实测 1.78 倍）；1.1 倍缩小时必须与面积平均**逐像素相同**（证明阈值生效）。
- `internal/fnos/icon_assets_test.go`：5 个派生产物必须两两字节一致 ——
  改了 logo 只重新生成一部分不会有任何报错，只表现为"有的地方换了、有的没换"，
  而浏览器标签与面板品牌图标走的正是内嵌那张，最容易漏。
- `scripts/e2e-gateway-check.py`：静态那 7 条守的是"实现有没有落在调用点上"
  （见 §6 里那张"守卫形同虚设"的表 —— 只查函数名存在的断言守不住任何东西）。
- 反向验证新增了**行为型**一层（`make reverse-verify-gotest`），因为静态断言
  看不出"写的那行有没有被执行到"：把锐化换成 `return out` 之后，函数名、
  常量、调用点一个不少，只有量过像素能量的单测才抓得住。

> 这一轮反向验证**当场抓到两条形同虚设的守卫**：`premultiplied` 改坏之后，
> 放大测试只查 R 通道，而预乘与不预乘算出的 R 完全相同（r 与 a 同比例缩小，
> 反预乘时又被除回去）；面积平均等权那条也没有用例覆盖，因为原有用例都是
> 整数倍缩放 —— 整数倍下所有源像素权重一样，等权也能算出同样的结果。
> 两条断言补上之后才真的 FAIL。

## 3. 与飞牛官方 fpk 规范的对齐

规范来源：[developer.fnnas.com](https://developer.fnnas.com/docs/guide/)，并以官方 `fnpack` 1.2.3 的 `create` 模板与真实打包结果做了交叉验证。

### 3.1 包结构

`fnpack` 打包前会做完整性校验，必填项如下（缺一不可）：

| 路径 | 类型 |
|---|---|
| `manifest` | 文件，且必选字段存在 |
| `config/privilege` | 文件，合法 JSON |
| `config/resource` | 文件，合法 JSON |
| `ICON.PNG` / `ICON_256.PNG` | 文件 |
| `app/` / `cmd/` / `wizard/` | 目录 |
| `app/{desktop_uidir}/` | 目录，声明 `desktop_uidir` 时必须存在 |

**`wizard/` 是最容易被漏掉的一个。**运行时生成的子应用包早期完全没有创建它，会导致 fnOS 侧「本地打包」的完整性校验直接失败，而且没有任何报错——表现为安装成功但图标永远不出现。现在 `BuildPackage` 显式创建该目录，并写入一个合法的空向导 `[]` 保证目录非空。

### 3.2 `app/` 这一层会被剥掉

这点极其容易搞错，也是本次重构中实际修正过的 bug：

```
源码包里   app/ui/config
安装后     $TRIM_APPDEST/ui/config
```

因为 **`app/` 目录里的内容会成为应用的 target 目录**，`app/` 这一层本身不存在于安装结果中。所以运行时做配置漂移检测时，读的是 `<安装目录>/ui/config`，而不是 `<安装目录>/app/ui/config`。同理，`install_callback` 里补可执行位的对象是 `${TRIM_APPDEST}/ui/index.cgi`。

### 3.3 manifest 字段

只使用官方文档定义过的键：

- `platform` 取 `x86` / `arm` / `all`，**不含**早期版本夹带的 `arch`；
- 打包脚本按目标架构注入 `platform`，保证 ARM 设备不会装上 x86 包；
- `desktop_applaunchname` 必须与 `app/{desktop_uidir}/config` 中 `.url` 下的入口 ID **一字不差**，否则点应用卡片打不开；
- `checkport = false`：子应用不真正监听所声明的端口，保持默认的 `true` 会让应用中心把图标标为异常。

`fnpack` 会在打包时自动往 manifest 追加一行 `checksum = <app.tgz 的 md5>`，手工打包路径必须复现这一行为。

### 3.4 入口 ID 约定

官方约定入口 ID 以 `appname` 为前缀并带稳定后缀，因此采用 `<appname>.main`，并与 `desktop_applaunchname` 保持一致。

### 3.5 打包产物结构（实测）

用官方 `fnpack build` 打包并解包，得到的确切结构如下，手工兜底路径据此复现：

```
<fpk>
├── manifest            fnpack 自动追加 checksum 行
├── app.tgz             内容 = app/* ∪ config/*
├── cmd/                生命周期脚本（main + 8 个钩子）
├── config/             privilege / resource
├── wizard/             install / uninstall 向导
├── ICON.PNG            64×64
└── ICON_256.PNG        256×256
```

注意 `app.tgz` 的内容是 `app/*` **并上** `config/*`——`fnpack` 会把包根的 `config/` 一并塞进 app.tgz。

### 3.6 wizard 的实际约束

官方文档列出了 `switch` 字段类型，但 `fnpack` 1.2.3 的内容校验**不接受**带布尔 `initValue` 的 `switch`（实测报 `File "uninstall" is not valid due to JSON format or content validation failure`）。`tips`、`text`、`radio` 均可用。因此卸载向导使用 `radio` 表达「移除 / 保留」二选一。

> 这是用官方工具实测得出的结论，文档与工具行为不一致时以工具为准。

## 4. 运行身份（privilege）

### 主应用

`fnos-app/config/privilege` 声明 `run-as: root`。官方推荐默认使用专用包用户，但本应用必须：

- 调用 `appcenter-cli` 安装 / 卸载**其它**应用（产品核心能力）；
- 读取宿主机视角的 `/proc` 套接字表与进程 fd；
- 访问 Docker 的 Unix Socket 枚举容器。

### 生成的子应用

同样显式声明 `root`，原因写在生成逻辑里：子应用包名形如 `qlink2d.alist-3f2a1c`（含点号）。当 `privilege` 未指定专用用户时，飞牛会依据 `appname` 自动派生一个，而 Linux 的 `useradd` 默认拒绝含点号的用户名，派生失败会让整个安装中断。此外 `install_callback` 需要给 `index.cgi` 补可执行位。

## 5. 生命周期脚本

`cmd/main` 遵循官方退出码约定：

| 命令 | 成功 | 失败 |
|---|---|---|
| `start` / `stop` | `0` | `1` |
| `status` | `0`（运行中） | `3`（未运行） |

用户可见的错误通过 `TRIM_TEMP_LOGFILE` 输出（官方约定），同时写入 `${TRIM_PKGVAR}/info.log` 便于排查。

### 子应用的 `main` 是刻意的空操作

子应用没有任何常驻进程，但飞牛应用中心是靠「应用是否处于运行态」来决定桌面图标是否显示的。因此 `start` 立即返回 0、`status` 恒为运行中。

**没有**按官方对静态应用的建议设置 `ctl_stop=false`：隐藏运行控制后，应用中心的运行态判定路径会随之改变，而「图标必须出现在桌面上」是本产品的核心承诺。在真机上验证过 `ctl_stop=false` 的行为之前，不拿这条主链路冒险。这是当前实现里唯一一处有意偏离官方建议的地方，特此记录。

### 卸载时的桌面图标清理

`cmd/uninstall_init` 读取 `wizard/uninstall` 收集的 `wizard_keep_icons`，默认把本应用生成的桌面图标一并卸载（`keep` 则保留）。清理动作全部 `|| true`——卸载主应用的成功不被清理动作绑架。

**命名空间只认 `qlink2d.` 一个**，与 §2.4 是同一条边界。这里曾经出过本应用最严重的一次越权：脚本里硬编码了 `MANAGED_PREFIXES="qlink2d. othertool. anothertool."`，把其它工具生成的图标当成"本应用遗留"一并卸载，**真实地删掉过用户用其它工具生成的图标**。修的时候只改 Go 侧的 `IsManagedApp` 是不够的——shell 脚本是另一份实现，两处必须一起改。

另有一道**覆盖升级保护**：部分飞牛版本在覆盖安装流程里同样会触发卸载钩子，若此时照常清理，升级完成后桌面上剩下的全是"已被卸载"的僵尸图标（真机踩过，表现为点开报 10016）。`upgrade_init` 因此在升级前写 `/tmp/qlink2desktop-upgrading` 时间戳，本钩子在 10 分钟窗口内直接跳过清理。

## 6. 可测性

安装编排完全依赖 `CLI` 接口抽象，测试用 `FakeCLI` 在毫秒级覆盖全部分支，不需要真机。`FakeCLI.InstallRoot` 会把包里的桌面入口配置**真实落盘**到模拟的安装目录，这样 `isStale`（配置漂移检测）才能返回真实结果，「已安装且配置正确 → 不重复安装」这条关键路径才可被测试。

同理，服务发现读 `/proc` 的部分通过 `ProcPath` 注入，反向代理与存储层各自可注入拨号器与目录。

### 网关等效端到端验证

`internal/httpapi/server_test.go` 覆盖的是**处理器**语义，但真机白屏那类问题的成因在**网关之后**：路径前缀、尾斜杠、并发转发。用本机 `curl localhost:5900/` 复现不了，因为那时请求根本没经过网关。

`scripts/e2e-gateway-check.py`（`make e2e`）用两个 HTTP 代理精确复刻网关的两种转发方式，然后把浏览器视角的完整加载链路跑一遍：

| 断言组 | 覆盖的真机故障 |
| --- | --- |
| 入口尾斜杠自愈 | 卡在「正在加载界面…」 |
| 文档 + 文档中无根绝对路径 | 网关前缀下资源 404 |
| 每个关键静态资源的 Content-Type | `type="module"` 因 MIME 不对被拒 |
| **递归爬取 ES 模块 import 图** | app.js 里写错 `'./dom.js'` 这类路径，HTTP 状态码看不出来 |
| `/api/bootstrap` 单请求 | 网关并发转发不可靠导致启动挂起 |
| 鉴权边界（无口令放行 / 有口令 401 / 登录后放行） | 桌面 iframe 无法携带令牌 |
| 深链接按 `Accept` 分流 | 前端拿到 HTML 解析失败 |
| 扫描三端点：202 受理 → 轮询到终态 → 取消；范围非法一律 400 | 「请求超时：15 秒内没有响应」，而扫描其实还在跑 |
| 网段接口的「首选网段不是虚拟网卡网段」 | 扫到容器网络，真实设备一台都没有 |
| 帮助页模块经网关可取 + 导航里注册了 help 视图 | 说明写进了界面却取不到 / 入口没挂上 |
| 前端扫描异步化与「范围三选一」静态守卫 | 后端异步只做了一半，前端仍在等同步响应 |

import 图那一项是关键：模块路径写错时页面能打开、接口全通，只有交互静默失效——除了把整张图爬下来逐个请求，没有别的办法在不打开浏览器的情况下发现。

### 真浏览器启动期验证

上面的脚本断言的是**服务端送出了什么**，但真机上翻车的往往是**浏览器拿它做了什么**（缓存、预扫描、模块图失败）。`scripts/browser-e2e.py` 补上这一段：起后端 + 网关模拟器，用真实 Chromium（Edge）打开入口，等看门狗窗口过去，再读回页面实际显示的内容。

两种期望值覆盖两个方向：

```bash
# 正常版：应进入应用，且不误报诊断
python scripts/browser-e2e.py --exe .build/dev/qlink2desktop.exe --expect ok

# 故障版（把 import 改回旧布局再编译）：应停在启动页，并把 404 文件列全
python scripts/browser-e2e.py --exe .build/dev/qlink2d-degraded.exe --expect diagnostic
```

第二个方向尤其重要：它验证的是"诊断能力本身不是空壳"。只断言"页面里有看门狗代码"是不够的 —— 必须真的造一个故障，看它有没有把证据说出来。

**一切可见性判断都以计算样式为准。** 读回的快照里有两组字段：`*HiddenAttr`（元素的 `hidden` 属性，仅供排查）与 `*Visible`（`checkVisibility()` 的结果，用于断言）。这不是冗余 —— §2.11 那次"遮罩永远盖着应用"的事故，正是因为旧脚本只看属性：`boot.hidden === true` 一路断言通过，而遮罩实际一直显示在屏幕上。

### 窄屏 / 宽屏导航可用性验证

启动期正常**不等于**手机上能用（§2.19）。`scripts/browser-e2e.py` 在启动期那一段之后，
接着跑 `scripts/browser-mobile-check.js`，在同一批视口里各走一遍：

```
360×640   390×844   430×932   →  窄屏：底部固定条、图标+文字可见、触摸目标 ≥44×40、
按真实坐标点击能切视图、内容区为底部条留白、
侧边栏没有徽标节点、状态点整格不显示
1280×800                      →  宽屏：仍是左侧栏、状态点仍带文字可见、侧边栏没有徽标节点
```

窄屏另有一组**尺寸**断言：图标渲染 ≥20px、底条实测高 ≥52px、`.content` 的
`padding-bottom` ≥ 底条实测高度。加它们是因为反向验证暴露过一个洞 ——
把图标从 22px 改回 14px、把 `min-height` 从 46px 改回 30px，
"图标看得见""点得动能切换"**照样全绿**。能用和好看是两件事，后者也得有人守。

三个容易写错的地方，都是"验证脚本自己的坑"：

- **重叠判据要跟排列方向走**：窄屏是横向一排（比左右），宽屏是左侧竖列（比上下）。
  只比 left/right 的话，竖列里每项的 left/right 本来就一样，会假报重叠。
- **入口不带尾斜杠时必然有资源 404**：Chromium 预扫描器会抢跑预取几个相对资源
  （已知、无法从 HTML 侧消除）。所以这里**不**拿"控制台一条错误都没有"当断言，
  改成断言"**样式表真的生效**"（读 `.sidebar` 的计算样式：窄屏必须是 `fixed`，
  宽屏必须不是）—— 那才是"样式到底应用上了没有"的硬证据。资源告警只作为 NOTE 打印。
- **静态守卫与浏览器守卫要一起跑**：`e2e-gateway-check.py` 固定去找
  `.build/dev/qlink2desktop.exe`，找不到是**直接退出、一条断言都不跑** ——
  那看起来和"全绿"一模一样。反向验证脚本两个产物路径都要编，
  并且两种守卫的 FAIL 数分开打印，否则"没执行"会被误读成"没抓到"。

`internal/fnos/favicon_test.go` 另有一组针对 §2.20 的守卫，全部用 `httptest`
起真站点（不依赖外网）：ICO 各档位解码、PNG-in-ICO、AND 掩码透明、
"取最大的那一档"、"必须自己解 ICO"（断言标准库确实解不了，前提变了要立刻知道）、
离线模式一个请求都不发、失败结果进缓存。ICO 那几条尤其不能省 ——
它是标准库没有的能力，坏掉的表现是"图标默默退回默认值"，其余断言全都看不见。

§2.21（过程可见）另有两组守卫：

- `internal/httpapi/icons_resolve_test.go`：解析接口吃得下**整条链接**的表单数据
  （少一个字段就 4xx 的那个坑）、离线时说明是开关关掉了、草案没填完也不崩、
  自动图标不混进图标库；
- `internal/fnos/favicon_test.go` 里的 `EnsureAutoIcon*`：图标真的落盘、
  同一组输入只解析一次（**它迭代回报"变了"会形成一个自己喂自己的广播循环**）、
  地址变了必须重解析、非「自动」档不落盘、删除时文件与状态一起清。

### 反向验证：`scripts/reverse-verify.py`

`make reverse-verify` / `make reverse-verify-browser`。

这个脚本把每条守卫对应的事实**改坏**，确认检查真的会 FAIL，然后无条件还原。
它不是可选项：

> 「通过」和「没在测」长得一模一样。

本项目已经连续踩到过三种"守卫形同虚设"的形态，全都只有反向验证才能发现：

| 形态 | 表现 |
| --- | --- |
| 守卫盯着**没人调用的**函数 | 重构后断言还在跑，但检查的是一个薄壳 —— 全绿 |
| 断言只搜**子串** | 把 `views[i].IconAuto = s.deps.Service.AutoIconFile(l)` 改成 `= ""`，子串仍在，全绿 |
| 断言只搜**类名** | 把 `.icon-status { display:inline-flex }` 整条删掉、只留 `.icon-status:empty`，类名仍在，全绿 |
| 断言**选错了观测量** | 放大测试只查 R 通道 —— 而预乘与不预乘算出的 R 完全相同（r 与 a 同比例缩小，反预乘时又被除回去），这条用例白写 |
| 用例**只覆盖了退化情形** | 缩放用例清一色整数倍，而整数倍下所有源像素权重相同 —— 「按面积加权」和「等权」给出一样的结果，守了个寂寞 |

后两条是这一轮补的行为型反向验证抓出来的（见 §2.23 末尾）。
它们说明一件事：**"这条断言能 FAIL 吗"必须真的试一次**，
光看断言写得很具体是不够的。

写这个脚本时它自己也踩了两个坑，都值得记下来：

- **前端资源是 `//go:embed` 进二进制的**：改了磁盘上的 `editor.js` / `style.css`
  而不重新编译，浏览器跑的仍是旧代码 —— 四个前端场景第一次跑全部 MISS，
  差一步就得出"浏览器守卫形同虚设"的错误结论。所以补丁涉及前端时也必须重编译。
- **汇总行里夹着 ANSI 颜色码**：`通过 219 项\x1b[0m，失败 0 项`。
  不剥掉的话正则永远匹配不上，脚本会一口咬定"基线没跑起来" ——
  又一个同型陷阱。

第三个是自己后来长出来的：静态分支的 `finally` 里留了一句
`os.remove(backup)` —— 变量在上一版改用内存副本还原时被删了，这行没删。
它落在 `finally` 里，于是**第一个场景跑完就 NameError 崩掉**，
"脚本挂了"和"守卫没问题"在终端里看不出区别。教训是同一条：
这个脚本本身也是被验证的对象，它崩了不能当成通过。

第四个是这一轮踩到的，也是最值得记的一个：**它自己被中途打断时，
会把改动留在仓库里**。缩放那一轮的行为型验证被前台超时 SIGTERM 打断，
`internal/fnos/imageutil.go` 里留下了一行 `return out`（整个锐化被摘掉），
而 `go test` 全绿 —— 因为被测的就是那份被改坏的代码。
于是有了 `Workspace`：改动前把涉及的每个文件**落盘**备份（不是只放内存），
正常退出、收到信号、以及**下一次启动**都无条件还原。
"改坏 → 验证 → 还原"这条链上，还原失败与验证通过长得一模一样。

真视口那部分还加了一个 `--sections` 开关（`browser-e2e.py`），
让每轮只跑相关的那一段。**"反向验证太慢"的必然结果就是"有人省掉它"** ——
这个项目已经为此吃过一次亏。同理，行为型那一层只跑
`go test ./internal/fnos/ -run 'Resize|Sharpen|IconArtifacts'`：
全量跑一轮四十多秒，几条场景就是四分钟，而"慢"的下场就是"被跳过"。

### 行为型反向验证：`make reverse-verify-gotest`

静态断言只能看"代码里写了什么"，看不出"写的那行有没有真的被执行到"。
`return sharpenPremultiplied(out, sharpenAmount)` 换成 `return out` 之后，
函数名、常量、调用点一个不少 —— 静态守卫全绿，用户看到的图标会重新变糊。

所以凡是"改一下参数就悄悄失效"的实现（缩放、锐化、预乘），都由单测来守，
再由这一层反向验证证明那些单测**真的在测**。最后一条场景会真的重跑
`cmd/iconforge` 覆盖 5 个产物，跑完从备份还原。

另有一类不是"守卫失效"而是"代码自以为做了容错"：`GroupPorts` 初版写了
一段"后来的套接字补上前一个的空缺"，单元测试直接证明它**永远不执行**
（见 §2.22）。这种死代码同样只有反向验证式的主动证伪才能发现 ——
它比没有更危险，因为它让"这里做过容错"看起来是真的。

## 7. 图标管线

桌面图标从哪来，按优先级见 §2.20（上传 → 文字 → URL → 官方图标库 → 站点 favicon →
内置默认）。下面这条是**产品自身的**图标资源管线，与上面那条运行时的解析链无关。

```
QLink2Desktop.png (1536²)
        │  go run ./cmd/iconforge
        ▼
  fnos.ToIconSet → ResizeHighQuality   精确面积平均（预乘 alpha）+ 2× 以上补一道锐化
        ├─→ fnos-app/ICON.PNG                    (64)
        ├─→ fnos-app/ICON_256.PNG                (256)
        ├─→ fnos-app/app/ui/images/icon_{64,256}.png
        └─→ internal/fnos/assets/logo_256.png    go:embed，运行时默认图标
```

质量取舍与实测数据见 §2.23。两条要点：

- **产物必须全部重生成**。少更新一处不会有任何报错，只表现为"有的地方图标
  换了、有的没换"；浏览器标签与面板里的品牌图标用的是 `logo_256.png`
  转出来的 `icons/default-64.png`（运行时生成），漏掉内嵌那张就会出现
  "应用中心换了、页面里没换"。`TestShippedIconArtifactsStayInSync` 逐字节钉住。
- **五张图都从同一个入口缩放**，改缩放只需改 `ResizeHighQuality` 一处；
  `cmd/iconforge` 也不做自己的重采样，直接复用 `fnos.ToIconSet`。

为什么把 logo 编进二进制：本项目强调完全自包含——拷到哪台机器、怎么部署，默认图标都长一个样，不依赖安装目录里恰好存在某个图片文件。

## 8. 已知的取舍

- **`ctl_stop`**：见 §5。
- **`PortalPort`**：设置页暴露的「门户端口」目前仅持久化、未驱动 TCP 监听（接入统一网关后默认无 TCP）。需要直连调试时用 `PORT` 环境变量。
- **手工打包路径**：仅在官方 `fnpack` 完全不可用时启用，结构已对齐实测产物，但仍建议优先使用 `fnpack`。
- **包内权限位恒为 0666**：在 Windows 上构建时，NTFS 没有 x 位，`chmod +x` 不生效，`fnpack` 只能记 0666。历史上每个包都如此，而它们在真机上都能正常安装并启动（应用界面能打开，就是 `cmd/main` 被执行过的证据），说明飞牛侧不依赖这个位。`scripts/verify-fpk.py` 因此在 Windows 上把它报为 WARN、在 POSIX 上报为 FAIL —— 在 Linux 上它确实是缺陷。
- **无斜杠入口下会有 1～2 条 404**：Chromium 的预扫描器会按文档基准抢跑预取 `<link>` / `<script src>`，这一条无法从 HTML 侧消除（详见 §2.9）。应用不受影响。
